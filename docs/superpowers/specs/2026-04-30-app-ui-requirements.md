# Codex Switch App UI 需求文档

日期：2026-04-30  
适用范围：`Codex Switch` Tauri 桌面端当前重构阶段  
文档定位：可评审、可落地、可继续拆任务的 UI 需求基线

## 1. 文档定位与目标

这份 UI 需求文档面向当前 `Codex Switch` 桌面端重构阶段，目标不是产出一份泛化 PRD，而是形成一份同时可用于评审、设计对齐和客户端实现拆分的界面需求基线。文档默认覆盖全量桌面端体验，包括主窗口、托盘快切面板、全局反馈、页面状态和基础视觉原则。

产品定位上，`Codex Switch` 是一个以桌面软件体验为核心的 Codex 多账号管理器，不应呈现为典型 Web SaaS 后台。界面设计需要服务三个核心目标：

- 降低多账号切换和识别成本
- 把高频轻操作与低频重操作分层承载
- 在保持 `.codex` 数据兼容的前提下，让信息结构和交互模型足够稳定，支持后续 Tauri 主线继续迭代

本次 UI 需求范围包括：

- 托盘入口与快速切换体验
- 主窗口一级导航与各功能页布局
- `账号`、`Usage`、`Provider Sync`、`状态`、`设置` 等页面需求
- 空态、加载态、成功态、失败态、禁用态等通用状态
- 桌面感、层级感、信息密度等基础视觉原则

本次不展开的内容包括：

- 品牌视觉系统细则，如完整色板、字号表、图标规范
- 动效实现细节与逐帧过渡规范
- 后台服务、数据模型、接口协议本身的技术实现设计
- 移动端或网页端适配需求

## 2. 全局信息架构与入口分层

整体信息架构采用“双入口 + 单主窗口 + 明确分层”模式。产品不应把所有能力塞进托盘，也不应回到多个分散窗口并存的结构，而是把高频轻操作和低频重操作稳定拆开。

全局结构如下：

- 托盘入口：承担高频、轻量、即时操作
- 主窗口：承担完整、低频、需要理解上下文的管理操作
- 浏览器或系统弹出流程：仅承载外部授权、文件选择、系统权限等特殊流程

入口职责如下：

- 托盘只负责当前账号摘要、快速切换、快速刷新、打开主窗口、进入设置、退出应用
- 主窗口负责账号管理、Usage 查看、Provider Sync、状态与诊断、偏好设置等完整能力
- 任何需要连续操作、理解数据上下文、查看详细结果的任务，都应进入主窗口完成，而不是继续堆在托盘内

主窗口导航如下：

- 主窗口始终作为唯一的完整管理容器，避免长期保留多个平级业务窗口
- 一级导航稳定覆盖核心模块：`账号`、`Usage`、`Provider Sync`、`状态`、`设置`
- 导航形态可以在实现阶段选择顶部分段 Tab 或桌面化侧边导航，但信息架构必须保持稳定，不能因壳层样式变化而改变模块边界
- 默认从托盘打开主窗口时进入 `账号` 页

跨入口跳转规则如下：

- 从托盘点击“主窗口”时，默认落到 `账号` 页
- 从托盘点击“设置”时，应直接打开主窗口并定位到 `设置` 页，而不是再开一个独立设置窗
- 浏览器登录、文件导入、Provider 恢复等外部动作完成后，应返回原页面上下文，并给出明确结果反馈
- 主窗口内部切页不应丢失当前页面局部状态，例如筛选条件、已选账号、滚动位置

页面边界如下：

- `账号` 页是账号列表、排序、导入、切换、主信息查看的唯一主阵地
- `Usage` 页是用量数据的独立阅读空间，强调趋势和来源说明，而不是重复账号管理动作
- `Provider Sync` 页承载目标 provider 选择、同步、切换、备份恢复与清理
- `状态` 页承载运行状态、日志、错误定位信息，不与设置混排
- `设置` 页只承载偏好项、运行项和路径说明，不混入高频业务操作

## 3. 托盘 UI 需求

托盘是整个产品的高频入口，但不应承担“完整管理界面”的职责。它的目标只有三个：让用户快速确认当前账号状态、快速切换账号、快速进入主窗口。托盘体验应强调短路径、低认知负担和强可读性，而不是功能堆叠。

托盘界面由 3 个区域构成：

- 顶部摘要区
- 中部快切区
- 底部快捷动作区

### 3.1 顶部摘要区

摘要区用于回答“我现在是谁、当前状态如何”。这里应展示：

- 当前激活账号
- 当前账号的简要 usage 摘要
- 一个明确可点击的刷新动作

摘要区要求如下：

- 当前账号必须是首要信息，默认使用邮箱作为识别主字段
- Usage 只展示最关键的两项摘要，例如 `5H` 与 `7D` 百分比，不在托盘里展开解释性说明
- 刷新动作必须可见且单击可达，反馈要明确，避免用户不确定是否已经触发
- 当没有激活账号时，摘要区要明确显示“未检测到账号”或等价文案，不能留空

### 3.2 中部快切区

快切区只负责“看列表并切换”，不承担账号管理。这里展示全部可切换账号，并满足以下要求：

- 列表按主窗口账号页的顺序展示，托盘不做二次排序
- 当前账号在原位置高亮，不置顶、不跳位
- 每一行至少展示邮箱和账号类型
- 如果有空间，允许补充 `5H / 7D` 微型指标；如果空间不足，优先保证邮箱可读性
- 列表支持内部滚动，不因为账号变多而无限拉高托盘高度
- 点击整行即可切换账号，不要求用户再点二次按钮
- 托盘账号行中不放删除、编辑、排序、导入、恢复等重操作

账号行交互和视觉要求如下：

- 当前账号要有稳定且明显的选中态
- 非当前账号 hover 时需要有清晰反馈，体现“可立即切换”
- 邮箱过长时允许截断，但应保证前缀和识别度；是否显示完整邮箱遵循全局设置
- 类型信息应弱于邮箱，不应抢主视觉层级
- 切换动作触发后，应立即进入进行中状态，并在成功后关闭托盘或保持稳定反馈；失败时必须保留当前高亮并给出错误提示

### 3.3 底部快捷动作区

底部快捷动作区保留：

- 打开主窗口
- 进入设置
- 退出应用

这一区域的要求是：

- 动作数量保持克制，避免底部按钮区演变成功能堆栈
- “打开主窗口”优先级最高，文案应稳定，不与“账号管理”“控制台”等命名混用
- “设置”不应再打开独立设置产品体系，而应进入统一主窗口中的设置页
- “退出”应作为全局动作保留，但视觉优先级低于主窗口入口

### 3.4 托盘状态要求

- 加载态：首次打开时如数据未就绪，应显示轻量骨架或占位，而不是闪烁空白
- 空态：没有可用账号时，中部区域显示空态说明，并给出“去主窗口导入账号”这样的下一步引导
- 成功态：刷新、切换成功后应有短时成功反馈，但不应造成界面跳动
- 失败态：切换失败、刷新失败时，应在托盘内给出单行错误反馈，并允许用户继续操作
- 禁用态：进行中的刷新或切换动作需要临时禁用重复触发，避免多次提交
- 大列表态：账号很多时，托盘仍只做快切，不增加搜索、分组、筛选作为第一阶段必选项

### 3.5 托盘边界

托盘不负责以下能力：

- 账号导入
- 账号排序
- Provider 管理
- 详细诊断查看
- 复杂设置修改

## 4. 主窗口框架 UI 需求

主窗口是产品的完整工作台，承担所有需要理解上下文、查看细节、执行连续操作的任务。它的设计目标不是做成网页后台，而是做成一个稳定、克制、具有桌面工具感的主控界面。

主窗口由 4 个稳定区域组成：

- 一级导航区
- 页面标题与上下文操作区
- 主内容区
- 全局反馈区

### 4.1 一级导航区

- 导航项固定为核心模块，不随状态频繁变化
- 导航名称统一使用面向用户的中文命名，避免中英混排导致层级混乱
- 当前激活模块必须有明显选中态
- 导航本身只负责切页，不承载复杂业务信息
- 导航项数量控制在 5 个左右，避免继续横向扩张

当前阶段建议一级导航为：

- `账号`
- `Usage`
- `Provider Sync`
- `状态`
- `设置`

后续可以进一步统一为纯中文命名，但在这一版需求中先强调命名一致，不强制立即改名。

### 4.2 页面标题与上下文操作区

- 每个一级页面进入后都要有稳定标题，帮助用户确认当前位置
- 标题区允许放少量与当前页面强相关的操作，例如“刷新 Usage”“发起同步”“保存设置”
- 标题区不应承载全局操作，也不应与页面内容区的工具栏重复
- 标题、副标题、上下文说明三者层级要清晰，不能所有文字都使用同一视觉权重
- 当页面存在重要状态时，可在标题区显示轻量说明，例如“最近更新时间”“当前 provider”“诊断事件数”

### 4.3 主内容区

- 主内容区是信息密度最高的区域，应优先保证内容可读性和扫描效率
- 页面应采用卡片、分组块、列表、明细区等桌面化布局，而不是大面积无边界长表单
- 页面内部需要允许局部滚动，但应尽量避免整窗多层滚动叠加
- 双栏、三栏布局只在有明确主次关系时使用，不能为了“填满屏幕”机械分栏
- 对于主要列表页，应保证列表和详情信息之间的关系清晰，避免用户在多个区域反复找状态

### 4.4 全局反馈区

- 主窗口内需要有统一反馈机制，承载成功、失败、进行中提示
- 反馈出现位置应稳定，避免不同页面各自弹出不一致的提示样式
- 反馈文案应回答三个问题：正在做什么、是否成功、失败原因是什么
- 短时成功反馈可以自动消失；失败反馈应允许用户看清信息后再继续操作
- 不建议将所有结果都做成模态弹窗，优先使用轻量顶部条、页内消息或内联状态

### 4.5 跨页一致性

- 所有一级页面应共享统一的间距、卡片边界、标题样式和操作区规则
- 空态、加载态、错误态的表现方式要统一，不同页面只替换内容，不替换交互逻辑
- 页面切换不应造成明显布局跳变，壳层尺寸和主要结构要尽量稳定
- 从外部动作返回时，用户应能回到原来的上下文，而不是被强制送回首页
- 主窗口关闭再打开时，是否记忆上次页面可以作为增强项，但默认至少要支持从托盘按目标进入指定页面

### 4.6 窗口尺寸与适配

- 主窗口默认尺寸应优先适配桌面端日常使用，不追求极端紧凑
- 页面布局应在较窄窗口下保持可用，至少保证核心信息不重叠、不截断到不可读
- 当窗口缩小时，次级信息可以收敛，但主任务路径不能消失
- 不要求做响应式网页那种多断点系统，但需要具备基本的窗口伸缩适配能力

## 5. 页面级 UI 需求

### 5.1 `账号` 页

`账号` 页是主窗口中最核心的业务页，负责账号导入、账号识别、账号切换、账号排序与当前账号摘要展示。它既是账号列表页，也是账号管理页。

#### 5.1.1 页面目标

- 让用户快速识别当前有哪些账号
- 让用户能安全、明确地导入账号
- 让用户能低成本切换账号
- 让用户能理解当前激活账号及其核心状态
- 让账号顺序成为全局唯一真源，并影响托盘快切顺序

#### 5.1.2 推荐结构

页面建议采用“左侧列表 + 右侧摘要”的双栏结构：

- 左侧为账号列表与列表级操作
- 右侧为当前账号摘要、登录任务状态和辅助说明

列表级操作建议放在顶部工具区，至少包括：

- 导入当前账号
- 导入备份账号
- 浏览器登录
- 刷新当前账号 usage

#### 5.1.3 账号列表需求

账号列表中的每一项至少展示：

- 邮箱
- 当前激活状态
- 账号类型或 tier
- 数据来源
- 排序相关信息或可视化顺序位置

交互要求如下：

- 点击账号行或明确的“切换”动作即可切换账号
- 当前账号需要有稳定选中态和状态标签
- 列表顺序应为全局唯一真源，并驱动托盘快切顺序
- 第一阶段允许先展示稳定顺序；第二阶段补齐拖拽排序或上移下移
- 删除账号属于主窗口职责，但需要与切换操作明确区分，避免误触
- 当前账号不应因“正在使用”而自动置顶

#### 5.1.4 当前账号摘要区需求

摘要区至少展示：

- 当前激活账号邮箱
- 账号 tier 或类型
- 最近一次 usage 快照摘要
- usage 数据来源
- 登录任务状态或最近登录结果

如果没有当前账号，应展示明确空态，并引导用户进行：

- 导入当前账号
- 导入备份
- 浏览器登录

#### 5.1.5 特殊状态

- 无账号空态：说明当前尚未导入账号，并突出下一步行动
- 切换进行中：禁用重复切换，保留当前列表结构不跳动
- 切换失败：账号列表不变，错误信息进入统一反馈区
- Usage 未刷新：允许显示占位，不应阻塞账号列表使用
- 浏览器登录进行中：右侧区域显示当前任务进度或最近消息

#### 5.1.6 当前阶段重点收口

P0 必须具备：

- 导入当前账号
- 导入备份账号
- 浏览器登录
- 显示账号列表
- 切换账号
- 展示当前账号摘要

P1 建议补齐：

- 手工排序
- 删除账号
- 批量管理能力

### 5.2 `Usage` 页

`Usage` 页用于承载当前激活账号的用量阅读体验。它不应只是账号页侧边卡片的放大版，而应成为用户查看 quota 状态、刷新来源和时间信息的独立页面。

#### 5.2.1 页面目标

- 明确展示当前账号的 usage 快照
- 强化 `5H` 与 `7D` 两类指标的区别
- 告诉用户数据来自哪里、何时更新
- 在数据不可用时提供可理解的解释，而不是只显示空白

#### 5.2.2 推荐结构

页面建议采用“主指标区 + 信息说明区”双栏结构：

- 主指标区展示 usage 卡片、进度条、重置时间
- 侧边说明区展示来源、更新时间、模式说明

#### 5.2.3 核心内容

主指标区至少包含：

- `5 小时` 使用百分比
- `7 天` 使用百分比
- 对应重置时间
- 进度可视化组件

说明区至少包含：

- usage 数据来源
- 最后更新时间
- 当前使用模式，如 `Automatic` 或 `Local Only`
- 必要的提示文案，例如“当前为缓存数据”或“仅本地推断”

#### 5.2.4 状态要求

- 无数据空态：明确说明“暂无可展示数据”，并提示用户刷新或返回账号页
- 部分数据缺失：保留可显示部分，不因某项缺失而整页不可用
- 刷新进行中：保留现有数据显示，并增加进行中标识
- 刷新失败：展示失败原因和上一次有效快照时间

#### 5.2.5 页面边界

- 不承载账号导入或切换主流程
- 不混入 provider 配置操作
- 不把诊断日志直接插入主内容区

### 5.3 `Provider Sync` 页

`Provider Sync` 页是偏工具化、偏运维感的一页，用于承载 provider 状态、切换同步和备份恢复。它可以信息密度更高，但仍需保持结构清晰，不应演变为原始日志堆叠。

#### 5.3.1 页面目标

- 展示当前 provider 状态
- 告诉用户不同数据面上的 provider 分布情况
- 允许用户指定目标 provider 并执行同步
- 提供备份恢复和清理能力

#### 5.3.2 推荐结构

页面建议采用“左侧状态面板 + 右侧操作面板”的双栏结构：

- 左侧展示状态分布，如 rollout 日志分布、SQLite 分布
- 右侧展示同步动作、目标 provider 输入区、备份列表

#### 5.3.3 同步操作区需求

操作区至少包括：

- 当前 provider 展示
- 目标 provider 输入或选择
- `同步现有`
- `切换并同步`
- 已配置 provider 列表摘要
- 备份数量与空间占用摘要

交互要求如下：

- 目标 provider 输入必须有合法性校验
- 用户发起同步后，应显示明确进行中反馈
- “同步现有”和“切换并同步”需要在文案和结果反馈上清晰区分
- 如果同步会影响当前环境，应在执行前通过说明文案降低误操作风险

#### 5.3.4 备份区需求

备份区至少支持：

- 查看备份列表
- 选择一条备份
- 恢复选中备份
- 清理旧备份

备份行至少展示：

- 目标 provider
- 创建时间
- 体积大小
- 可识别的备份标识

交互要求如下：

- 恢复动作依赖显式选中，不能默认误恢复
- 清理旧备份属于带风险操作，应要求明确确认
- 恢复成功或失败都必须有用户可见结果

#### 5.3.5 状态要求

- 无分布数据时，要显示明确空态，而不是空白面板
- 无备份时，显示“暂无备份记录”
- 同步进行中时，关键按钮禁用或显示 loading
- 失败时要区分输入问题、同步问题和恢复问题

### 5.4 `状态` 页

`状态` 页是对当前 `Diagnostics` 页的扩展定义，不应只是一串事件日志。它应成为一个“混合状态面板”，同时展示账号运行状态、本地运行上下文和安全脱敏后的诊断信息。

#### 5.4.1 页面目标

- 帮助用户快速判断应用当前是否正常工作
- 为排查登录、usage、provider 同步问题提供上下文
- 展示关键本地路径和运行信息，但不暴露敏感 token

#### 5.4.2 推荐结构

页面建议分为 3 个区域：

- 状态摘要区
- 运行时与路径信息区
- 最近诊断事件区

#### 5.4.3 状态摘要区

摘要区建议展示：

- 当前激活账号摘要
- 当前 usage 摘要
- 归档账号数量
- 最近一次关键操作结果

这一区域的重点是“看一眼知道大体是否正常”，不需要承载完整操作。

#### 5.4.4 运行时与路径信息区

运行时信息至少包括：

- 当前运行时类型
- 主窗口或托盘宿主模式
- `.codex` 相关数据路径
- 诊断日志路径

展示原则如下：

- 允许复制路径或打开目录作为增强项
- 不展示敏感文件内容
- 不直接展示访问令牌、刷新令牌或原始授权数据

#### 5.4.5 最近诊断事件区

诊断事件区用于展示近期可读的、安全脱敏后的事件流。要求如下：

- 事件按时间倒序或类别清晰展示
- 分类字段与消息字段视觉分层明确
- 无事件时显示空态
- 支持长文本换行，但应保持扫描节奏
- 页面打开时应刷新最新状态快照

#### 5.4.6 当前阶段收口方向

P0：

- 事件列表可读
- 运行时与路径可见
- 激活账号和 usage 的基础摘要可见

P1：

- 分区更完整的状态卡片
- 打开本地目录与导出安全诊断摘要

### 5.5 `设置` 页

`设置` 页是应用偏好控制中心，用于承载一般偏好、usage 策略、显示隐私与高级工具入口。它不应成为业务功能杂糅区，但应足够支撑日常维护与个性化设置。

#### 5.5.1 页面目标

- 让用户管理应用级偏好
- 让设置变更具备“立即生效”的桌面端体验
- 在必要时提供高级维护入口

#### 5.5.2 推荐结构

设置页建议按分组组织，而不是单一长表单。推荐分组如下：

- `General`
- `Privacy`
- `Usage`
- `Advanced`

当前阶段可先用中文标题表达这些分组，但结构上应预留分组扩展能力。

#### 5.5.3 General 组

建议包含：

- 开机启动
- 是否显示完整邮箱
- 与桌面行为相关的基础偏好项

要求如下：

- 开关型设置应支持立即生效
- 每个设置项都要有简短说明，明确其影响范围

#### 5.5.4 Usage 组

建议包含：

- 是否启用 usage 刷新
- usage source mode 选择

要求如下：

- `Automatic` 与 `Local Only` 的区别要可理解
- 切换后立即持久化，不需要单独保存按钮
- 如果某个模式会影响数据完整性，应有提示说明

#### 5.5.5 Privacy 组

建议包含：

- 是否显示完整邮箱
- 诊断信息显示范围相关设置

原则如下：

- 隐私相关项需要明确影响哪些页面
- 默认值应优先保护敏感信息显示

#### 5.5.6 Advanced 组

建议包含：

- 查看或打开 `.codex` 数据目录
- 查看日志目录
- 导出安全诊断摘要
- 未来的清理缓存、清理日志等维护动作

要求如下：

- 涉及删除或清理的动作必须先确认
- 操作后必须展示成功或失败结果
- 高级动作默认视觉优先级低于普通偏好项

#### 5.5.7 状态要求

- 设置加载失败时，页面要明确提示，不要默默回退默认值
- 某项设置保存失败时，仅该项和全局反馈需要提示，不影响其他设置可用性
- 系统能力受限时，例如无法开启开机启动，需要给出清晰错误原因

## 6. 通用状态与反馈规范

为了保证全局一致性，所有页面和托盘都应共享一套状态与反馈语言。

### 6.1 加载态

- 首次加载时使用轻量占位或骨架，不使用整页白屏
- 二次刷新时尽量保留现有内容，只增加局部进行中状态
- 长耗时任务要有明确文案，例如“正在同步到 openai…”

### 6.2 空态

- 空态必须解释“为什么没有内容”
- 空态必须提供下一步动作或明确引导
- 空态文案要贴合页面上下文，不能所有页面都用“暂无数据”敷衍

### 6.3 成功态

- 成功反馈应短、稳、可确认
- 优先使用非打断式反馈
- 对用户有结果影响的动作要明确反馈完成，例如“账号已切换”“备份已恢复”

### 6.4 失败态

- 错误信息至少告诉用户哪一步失败
- 如果能恢复，应提示建议动作
- 不可恢复错误与可重试错误的表达方式要不同
- 失败后应尽量保持当前界面可继续操作

### 6.5 禁用态

- 进行中的按钮要进入禁用态或 loading 态
- 禁用时需要保留可理解的视觉状态，不能仅靠颜色变浅
- 禁用必须有原因，避免用户误以为界面失效

### 6.6 确认态

- 删除、恢复、清理、覆盖等高风险操作需要确认
- 确认弹层文案要明确对象和影响范围
- 确认态不应过度使用，避免用户疲劳

## 7. 基础视觉原则

这一版需求只定义视觉方向，不细化到颜色值和字号表。

### 7.1 整体气质

- 视觉方向应偏桌面工具，而不是网页运营后台
- 组件风格要克制、稳定、可信赖
- 页面应有明确容器边界和层次，不做大面积无分隔平铺

### 7.2 信息密度

- 保持中高密度，但不能拥挤
- 高频识别信息优先放在稳定位置
- 次级说明文字用来辅助理解，不抢主视觉

### 7.3 层级与容器

- 一级层级通过页面标题、导航选中和主卡片承载
- 二级层级通过卡片标题、分组标题和轻量边框区分
- 同一区域内不应混用过多视觉语言

### 7.4 控件风格

- 按钮风格应区分主操作、次操作和危险操作
- 列表行应具备清晰 hover、selected、disabled 状态
- 输入框和开关组件要优先强调可操作性与可读性

### 7.5 文案与命名

- 面向用户的主文案优先中文统一
- 模块命名、按钮命名、状态命名要前后一致
- 避免同一动作在不同页面出现不同叫法

### 7.6 桌面感

- 适当保留窗口感、面板感、工具栏感
- 控件尺寸应适配鼠标操作，不必过度放大成触屏尺寸
- 页面切换与反馈要稳定，避免移动端式夸张动效

## 8. 实现优先级建议

### 8.1 P0

必须先收口的内容：

- 托盘摘要、快切、主窗口入口、设置入口、退出
- 主窗口稳定壳层与 5 个一级模块
- `账号` 页导入、切换、当前账号摘要
- `Usage` 页核心指标与来源信息
- `Provider Sync` 页同步与备份基础闭环
- `状态` 页基础摘要与诊断事件可读化
- `设置` 页立即生效的核心偏好
- 全局统一反馈机制

### 8.2 P1

建议在 P0 后补齐：

- 账号排序能力
- 账号删除能力
- `状态` 页运行时路径和资源打开能力
- `设置` 页高级维护分组
- Provider 相关更完整校验和确认

### 8.3 P2

增强项包括：

- 托盘更丰富的 usage 微指标
- 更细粒度的状态卡片和趋势视图
- 更强的搜索、筛选、批量管理能力
- 更完整的视觉系统规范

## 9. 验收口径

这版 UI 需求验收不以“像不像网页后台”为标准，而以以下问题是否被清晰回答为准：

- 用户是否能快速知道当前正在使用哪个账号
- 用户是否能低成本切换账号
- 用户是否能区分托盘和主窗口各自职责
- 用户是否能在主窗口内找到完整管理路径
- 用户是否能理解 usage、provider、状态、设置各模块边界
- 用户在成功、失败、空数据、加载中等状态下是否都能得到明确反馈

如果以上问题都能被稳定回答，这版 UI 需求就算达到了当前重构阶段的目标。
